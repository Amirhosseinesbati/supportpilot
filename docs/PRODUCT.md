# SupportPilot product scope

SupportPilot is an evidence-based support workspace for Northstar Supply, a fictional premium home-office retailer. The local demonstration uses synthetic customers, products, orders, policies, and conversations. A second workspace, Harbor Workroom, exercises isolation. The intended buyer is a retailer that wants an installed support assistant customized to its catalog, policy sources, and commerce/support systems.

## Operator and customer journeys

1. **Knowledge administration.** An admin uploads a PDF, Markdown, or CSV source (10 MB maximum). The service validates the file, stores a SHA-256 version, extracts sections or PDF pages, chunks the text, and runs an ingestion job. A draft is published by an admin after processing. Queued or running jobs can be cancelled, failed/cancelled jobs retried, and documents replaced or deleted. The console shows status and recent progress.
2. **Grounded conversation.** A signed-in customer uses the compact widget; staff see the conversation in the inbox with evidence and order context. The local demo uses a deterministic answer fixture. Connected mode calls a configured model. Source buttons reopen a published current or historical passage with its effective date. If the required source or verified order is absent, the assistant asks for clarification.
3. **Order investigation.** Order lookups bind to the authenticated customer's server-side identity. A typed order number does not grant access. Admin APIs create customer logins, catalog products, and local orders with lines and shipments for an installed pilot. The demo guest challenge can verify a local synthetic order; it sends no message. Connected guest verification requires a separate channel and is not provided by the simulator.
4. **Return action.** The server checks item quantity, prior returns, delivery date, category, condition, and late-delivery exception. Orders with split shipments require every shipment to be delivered before a return can execute because shipments are not mapped to individual lines; the policy window uses the earliest delivery date and disables the late exception for these orders. Eligibility is rechecked when an operator approves. Eligible standard returns are recorded locally. Exception cases create a proposal for an operator. The operator can approve, edit, reject, or expire the exact version. A ledger and unique return record support idempotent local execution. No refund occurs.
5. **Human handoff.** Escalation makes a local ticket with the recent customer problem, citations, verified customer-scoped order context, attempted lookup summary, and unresolved questions. Staff can reply in the linked conversation and resolve or reopen the ticket.

The console includes Inbox, Knowledge, Approvals, Tickets, Connectors, Evaluation, and a customer widget preview. Its visual identity uses warm off-white surfaces, navy text, teal selection, and amber exceptions. On desktop, the inbox places the conversation beside its evidence and order context; mobile presents switchable context sections. The evaluation page shows recorded results only when the API supplies a run.

## What the local demo demonstrates

The recommended walkthrough starts with `cust_ns_demo_001`, `ord_ns_demo_001`, and `conv_ns_demo_001`. Its monitor was promised on 2026-08-14 and delivered on 2026-08-26. On the 2026-09-27 reference date, the standard 21-day monitor window has ended, while the 45-day late-delivery exception remains open. The seeded `proposal_ns_demo_001` is awaiting operator review. A question about an undocumented device then demonstrates clarification rather than an invented answer.

The full generator produces 120 products, 800 customers, 3,000 orders over 12 months, 80 documents across ten categories, 400 historical conversations, and 40 proposals in two workspaces. See [DATA_CARD.md](DATA_CARD.md) for distributions and limitations.

## Boundaries and release status

DEMO runs local commerce/support data and deterministic answer fixtures. Admins can set a document's category and authority at upload; replacement versions preserve both, and each workspace's authority priority controls a resolvable conflict. CONNECTED has configuration paths for a model, a Shopify read-only external order adapter that mirrors verified orders into scoped local records, and Zendesk ticket creation through a durable local ticket and leased action ledger. Unknown Shopify SKUs require admin product-category configuration before a return. Live credentials and bounded live connector smoke tests have not been verified. The message SSE route delivers chunks after the graph completes; model-token streaming and first-token latency measurement are pending. The default local database is SQLite, while PostgreSQL/pgvector migrations and retrieval branches exist but have not been exercised here. The project is a pilot foundation, not a production-ready support team replacement. See [IMPLEMENTATION_STATUS.md](IMPLEMENTATION_STATUS.md) for the current evidence.
